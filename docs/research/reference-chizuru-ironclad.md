# 参考项目拆解：Chizuru Ironclad Skin

参考对象：Steam Workshop `3747644438` / NexusMods `914`。

本文件只分析产品结构、表现层级和工程经验。**不得复制、提取、转换或重新打包该 Mod 的人物、卡图、音频、动画、代码或特效资源。**该项目作者也明确限制其打包资产的复用和转换。

## 为什么它值得参考

这个项目不是单纯替换一张人物贴图，而是把战士的完整“角色表现链”统一成同一个主题：

- 角色选择人物与背景；
- 地图和顶部面板头像；
- 战斗人物、待机、入场、受击、死亡与胜利；
- 普通攻击、范围攻击、多段攻击、Cut-in 和全屏终结技；
- 出牌时的侧边立绘演出；
- 战斗 SFX / FX；
- 营火和商店反馈；
- 战败 CG；
- 多人模式手势和人物状态；
- 游戏内表现设置；
- 独立的配套卡面包。

这说明高完成度美化 Mod 的单位不是“卡牌或模型”，而是**每一个玩家会看到角色的界面和状态**。

## 可借鉴的五个工程原则

### 1. 动作按运行时语义路由，而不是每张卡写死一套动画

参考项目先判断攻击拓扑：单体/群体、单段/多段，再依据攻击强度选择动作层级。这样可以用有限的高质量动画覆盖大量卡牌，同时保证普通牌快速、高价值牌更有冲击力。

佐助项目采用自己的路由：

1. 先按卡牌语义选择剑术、雷遁、火遁、写轮眼、咒印或防御家族；
2. 再按单体/群体、单段/多段选择动作骨架；
3. 最后依据稀有度、能量、实际伤害和是否斩杀升级表现层级；
4. 卡牌可显式锁定动作，解决特殊结算和动画中断问题。

### 2. 华丽动作必须分级，而且可关闭

长 Cut-in 和全屏演出不能频繁触发，否则会拖慢战斗并失去“必杀”的稀缺感。默认策略：

- 普通牌只使用 Quick / Standard；
- Signature 允许短镜头强化；
- Cut-in 默认只用于高价值攻击；
- Finisher 默认要求斩杀或显式标记；
- 提供“快速战斗”“关闭 Cut-in”“低闪烁”和“关闭额外粒子”。

### 3. 丰富度包括非战斗立绘

仅有战斗模型和卡图仍会显得割裂。我们的完整目标包括：选人主立绘、地图头像、顶部头像、营火休息、营火锻造、商店反馈、胜利图、战败 CG、加载页和多人手势。

### 4. 高特效必须从第一天做性能设计

参考项目的更新记录显示，首播卡顿、悬停节点未清理、重复遍历战斗节点、特效锚点查找和首次资源加载都会造成问题。我们的要求：

- 进入战斗前按场景预加载核心资源；
- 大招资源按需预热；
- 缓存人物、目标、屏幕特效锚点；
- 粒子池复用，禁止每次出牌重新创建大量材质；
- Cut-in、卡牌悬停和临时 UI 必须可验证地释放；
- 对纹理尺寸、同时存活粒子数和显存预算设上限。

### 5. 版本与多人兼容必须成为架构的一部分

不同游戏分支可能使用不同动画接口；人物缩放、入场位置、死亡序列和长演出等待都可能在多人模式暴露问题。必须：

- Stable / Beta 分支分别记录兼容版本；
- Hook 有版本保护和原动画回退；
- 长演出不得阻塞战斗模型；
- 本地视觉节点不进入多人同步；
- 对特殊卡牌提供排除名单；
- 测试入场、待机、受击、死亡和结束回合。

## 我们不照搬的部分

- 不使用参考 Mod 的官方人物资产、配音、音效或动画；
- 不复制它的卡面构图、分镜或提示词；
- 不复制它的具体评分公式和阈值；
- 不将佐助强行套进另一角色的招式名称和动作节奏；
- 不默认高频触发全屏演出。

## 佐助项目的差异化目标

- 剑术强调短路径、拔刀、突刺和预判，而不是大幅度舞台动作；
- 雷遁以“集中命中点”和高速位移为核心；
- 火遁负责群体与大范围表现；
- 写轮眼负责锁定、反击和强化反馈；
- 咒印负责自伤、力量、献祭和形态牌；
- 最高层级使用麒麟或咒印二阶段，但保持 Hebi 时期设定统一。
